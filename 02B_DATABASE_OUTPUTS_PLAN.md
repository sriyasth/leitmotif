
# 02B_DATABASE_OUTPUTS_PLAN.md
## Plan 2B — Database Outputs (Scene Context + Objects)

This document defines **exactly what Plan 2B is allowed to write to the database**.

Plan 2B is responsible for **scene context and object understanding**, not identity or people recognition.

It must **not interfere with the identity pipeline** handled by Plan 2A and Step 3.

---

# Purpose of 2B Database Writes

2B should only persist information that is useful for:

• debugging and demo replay  
• analytics on detected objects  
• optional visualization tools (heatmaps / scene reconstruction)  
• contextual environment state  

2B is **not responsible for identity, embeddings, or contacts**.

---

# Tables 2B May Populate

## 1. scene_context_logs

Stores a log of scene-level context detected during a session.

Purpose:
- replay demo context
- debugging perception behavior
- analytics

### Table schema

```sql
scene_context_logs
------------------
id UUID PRIMARY KEY
scene_id TEXT
environment_label TEXT
events JSONB
timestamp BIGINT
raw_summary JSONB
created_at TIMESTAMP DEFAULT NOW()
```

### Example row

```json
{
  "scene_id": "scene_00124",
  "environment_label": "living_room",
  "events": ["object_detected"],
  "timestamp": 1720000000
}
```

Only one row should be written **per scene context update**, not per frame.

---

# 2. object_sightings

Stores individual object detections for debugging and analytics.

Purpose:
- reconstruct object positions
- build scene heatmaps
- track object importance across frames

### Table schema

```sql
object_sightings
----------------
id UUID PRIMARY KEY
scene_id TEXT
temp_id TEXT
label TEXT
confidence FLOAT
x FLOAT
y FLOAT
z FLOAT
distance_meters FLOAT
importance FLOAT
timestamp BIGINT
created_at TIMESTAMP DEFAULT NOW()
```

### Example row

```json
{
  "scene_id": "scene_00124",
  "temp_id": "obj_1",
  "label": "lamp",
  "confidence": 0.88,
  "x": 1.2,
  "y": 0.3,
  "z": 3.4,
  "distance_meters": 3.4,
  "importance": 0.44,
  "timestamp": 1720000000
}
```

Write **one row per detected object per update window**.

---

# Tables 2B MUST NOT Write

Plan 2B must never write to these tables:

### contacts
Handles enrolled people and their metadata.

### face_embeddings
Stores embeddings used for identity matching.

### motifs
Stores leitmotif audio mappings for people.

### user identity records
Any table that contains `user_id` assignments.

### enrollment tables
Used by the facial recognition pipeline.

These belong to:
- Plan 2A (face detection / embedding)
- Step 3 (identity resolution)

---

# Identity System (Reference Only)

The identity system operates separately using:

• Supabase  
• pgvector for face embeddings  
• cosine similarity matching  

Tables used there include:

```
contacts
face_embeddings
```

Matching workflow:

1. Face embedding generated by Plan 2A
2. Query nearest neighbor in pgvector
3. Cosine similarity threshold (~0.5–0.6)
4. Match → assign `user_id`
5. No match → trigger enrollment flow

Plan 2B **must not participate in this pipeline**.

---

# Data Flow

Scene perception pipeline:

```
Camera Frame
      ↓
2A Face Detection (Apple Vision)
      ↓
2B Scene Context + Objects
      ↓
SceneContextResponse
      ↓
Merge Layer
      ↓
Identity Matching (Supabase + pgvector)
      ↓
Audio Engine
```

2B only produces:

```
SceneContextResponse
```

and optional database logs:

```
scene_context_logs
object_sightings
```

---

# Claude Implementation Rules

When implementing 2B:

1. Always produce `SceneContextResponse` as the main output.
2. Only write to `scene_context_logs` and `object_sightings`.
3. Never write to identity-related tables.
4. Never assign or generate `user_id`.
5. Do not store embeddings.
6. Do not implement enrollment logic.

---

# Minimal Requirement for Hackathon

For the hackathon demo, persistence is optional.

If implemented, store:

• object_sightings  
• scene_context_logs  

Everything else should remain in memory.
